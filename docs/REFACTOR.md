# v0.3.0 改造说明（对照 main）

基线：`main` 的 `124ae02b697fff4cf8ca45038f19f8efc595a639`（v0.2.0）。
本次在 `codex/quest-core-refactor` 实施，0.3.0允许破坏旧接口兼容。
项目更名为Quest XR Bridge：发行包/CLI为quest-xr-bridge，Python导入为quest_xr_bridge；旧quest_crt导入不再提供。
冻结依据为2026-10-10用户实机确认，具体范围见[验收记录](ACCEPTANCE.md)。

## 量化比较：配置、公式与实测分开

| 指标 | main / v0.2.0 | OpenTeleVision公开默认图像路径 | 当前冻结版 |
|---|---|---|---|
| 视频采集配置 | 每眼1280×720@60目标 | 每眼1280×720@60 | 每眼1280×720@60 |
| 实际送显图像尺寸 | 本轮未复现CloudXR实测 | 1278×360/眼（裁边+隔行） | 1278×360/眼 |
| 每眼像素数 | 921,600（声明配置） | 460,080 | 460,080，约为720p的49.92% |
| 固定发布等待 | 不同外部视频管线，未量化 | 每帧0.03秒 | 0秒 |
| 理论刷新上限 | 60FPS目标，非本次实测 | 1/0.03=33.33FPS，尚未计入处理耗时 | 60FPS配置上限 |
| Quest真实新视频帧 | 本次没有可比实测值 | 未直接跑原版；本机参考复现为27.83FPS / 36.00秒 | 59.96FPS / 18.00秒 |
| 平均新视频帧间隔 | 未测 | 参考复现约35.93ms | 约16.68ms |
| 同窗冻结/网络丢包 | 未测 | 参考复现0 / 0 | 0 / 0 |
| 视频同时的姿态接收 | 前序基线已建链，本轮未重测真机 | 论文报告60Hz系统循环，非我们的实测 | 中位90.48Hz |
| 对外端口 | 8000+8001，共2个 | 随部署/模式变化 | 8000，共1个 |
| 支持的QCRT帧长度 | 604/628/636/804，共4种 | 不使用本项目QCRT协议 | 804，共1种 |
| 姿态输出坐标/JSON计算次数 | N个消费者每帧约N次 | 不作等价比较 | 同帧1次，消费者共享 |

**OpenTeleVision 的0.03秒等待会把视觉更新从60FPS采集降到约30FPS级别。** 严格说，
等待本身限制为33.33FPS；加上JPEG处理和发送才会更低。不能把60FPS相机配置当作60FPS头显画面。
我们的参考复现实际27.83FPS；保留显示几何/图像处理、移除等待后为59.96FPS，约2.15倍新帧更新率。
这比较的是本机前后版本；不声称所有OpenTeleVision部署固定为28或30FPS。
原版另有WebRTC路径；这里的0.03秒结论只针对用户选择的默认JPEG图像路径。
论文的640×480/眼、60Hz也是另一组配置，未与默认脚本混为同一实测。

### 同机姿态CPU微基准

以相同的有效804字节合成姿态，对照main与当前代码；每项预热100次、采样600次，交替顺序运行3轮。
下表为三轮中位数的中位数；p95也取三轮p95的中位数，单位微秒。原始结果见[measurements.json](measurements.json)。

| 每帧工作 | main中位 / p95（µs） | 当前中位 / p95（µs） | 中位变化 |
|---|---:|---:|---:|
| 解码+校验 | 56.99 / 64.11 | 54.62 / 61.74 | -4.2% |
| 1消费者坐标转换+JSON | 331.85 / 349.07 | 341.95 / 366.88 | +3.0% |
| 2消费者坐标转换+JSON | 674.39 / 726.63 | 343.13 / 365.69 | -49.1% |
| 4消费者坐标转换+JSON | 1334.54 / 1403.40 | 344.32 / 365.69 | -74.2% |

单消费者并没有提速：当前缓存/锁开销使该项中位增加约3%。主要收益在多消费者，
2个消费者约减少49%计算时间，4个约减少74%。这不是端到端延迟，也不包含网络、视频编码或机器人执行。
测试输入为合成数据，三轮微基准仍受调度/CPU频率影响，不作产品吞吐保证。

### 代码规模（非性能指标）

生产Python口径：根server.py加SDK包，不含测试/示例/脚本。main为10个文件、3223行；当前为14个文件、3805行。
新增通用视频后，代码并非所有口径都减少；本次重点是去掉品牌集成并明确职责，不以总行数冒充运行效率。

## 功能与行为差异

| 方面 | main / v0.2.0 | v0.3.0 |
|---|---|---|
| 服务管理 | 独立启动脚本、模块级运行态 | 同步QuestServer对象，start/stop/上下文，就绪后返回 |
| 端口 | 8000入口、8001输出 | 一个HTTPS8000入口、Viewer及输出 |
| 姿态上行 | QCRT WebRTC和WSS JSON回退 | 单一独立WebRTC数据连接 |
| 姿态协议 | 多种短包与804B兼容、视频标记耦合 | 严格v5/804B完整字段，视频状态分离 |
| 姿态输出 | 通用/ws及DIME固定时钟QSTR/UDP | 仅真实新帧/ws；同帧转换及JSON编码共享 |
| 视频来源 | ZED/Televiz/CloudXR专用集成 | 外部任意同步校正RGB，SDK托管GStreamer视频进程 |
| 视频传输 | 外部CloudXR管线 | 独立NVENC/WebRTC媒体连接，SBS单轨、GCC与NACK/RTX |
| 显示 | 相机品牌集成页面及专用视频层 | 同一XRSession/GL上下文，通用逐眼采样与显式显示几何 |
| 录制 | 默认开启 | 默认关闭，可选有界后台录制 |
| 旧数据处理 | 消费者可能看到残留状态 | Viewer/视频250ms新鲜度门限，断开清理 |
| 包结构 | 根server.py承载大量业务 | 按协议、坐标、姿态运行态、SDK、视频及路由分工 |

main已经有姿态与可选视频的隔离意图；本次将其收敛为SDK明确持有和回收的资源，
并将视频入口从专用外部系统改为通用RGB。不能将此前未完整实机验收的视频目标当成已达能力。

## 决策与理由

1. **两条WebRTC连接、一套SDK生命周期。** 姿态是低带宽最新值，视频是编码媒体；
   各自背压、拥塞与重连，避免视频处理堵塞姿态。两条连接仍共享物理网络/机器，不能承诺物理隔离。
2. **删除回退和实验业务。** 去掉WSS姿态上行、DIME/QSTR/UDP、固定输出时钟及品牌启动器，
   缩小接口面；保留通用输出、Viewer、坐标和可选录制。
3. **完整帧有界交接。** 采集线程只提交拥有明确内存所有权的RGB；固定两槽共享内存，
   待处理帧被新帧替代，正在使用的槽不被覆写。左右图一次提交并合成SBS，避免独立视频轨的眼间错帧。
4. **原生依赖按需加载。** 基础姿态无需GI/GPU；视频启用时才检查并试硬编。
   失败明确返回，保持姿态运行，不引入软件编码回退。
5. **严格接收能力协商。** 本机Quest对H.264规格有限制，因此支持并优先协商H.265 Main；
   不伪造SDP等级。整数H.264等级使用GStreamer接受的格式（如4而非4.0）。
6. **显式分眼显示。** 早期原生Cylinder在真机有解码但不可见，最终复用现有GL上下文，
   同一视频纹理逐眼采样。HUD两眼共用头部中心的同一块几何，避免各眼独立放置。
7. **冻结参考显示面，不增加深度重建。** 依据OpenTeleVision公开代码定义画幅，
   平面高8m、宽高比1.66667、中心[0,-1,-7]m；保留原生IPD和投影。
   它是显示几何而非真实物体距离；同步、校正和云台控制继续属于外部程序。
8. **恢复60FPS新帧。** 参考图像路径裁边、隔行及JPEG80保持，取消每轮0.03秒等待，
   按相机新帧驱动。本轮每眼实际1278×360，不能将其表述为完整720p60。
9. **关闭与重入可靠性。** DTLS transport所有权修复避免原生关闭异常；使用连接UUID抵御过期关闭，
   每次新媒体协商回收旧worker，限制跨连接原生资源累积，代价是重入启动等待。
10. **效率与可维护性。** 通用输出按新帧触发，坐标与JSON同帧只计算一次；慢消费者独立处理。
    SDK不劫持宿主信号或日志；CLI仅是SDK调用方。

## 验证与清理边界

已验证的短时结果、用户确认和未完成项目集中在ACCEPTANCE.md；不再保留调参流水账。
删除仓库内旧品牌集成、临时诊断页、故障注入样例、抓取图像和重复探针。
保留协议/生命周期/缓冲所有权/显示几何/资源释放等核心回归，以及一个端到端姿态自检入口。
原生运行库是视频部署依赖，不能作为“调试垃圾”删除；原始验收材料不进入公开Release。
